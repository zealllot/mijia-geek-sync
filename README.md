# mijia-geek-sync

**把米家自动化极客版的规则变成能进 git 的文件，然后全量对账推回去。**

极客版的规则只存在中枢里，改动靠在网页画布上拖节点，没有版本控制、没有 diff、没有 review。
这个工具把它变成：拉下来是文件 → 改文件 → 看 `git diff` → 推回去。

底层通过 [`@eyaeya/xgg-cli`](https://github.com/eyaeya/xiaomi-central-hub-gateway-cli)（GPL-3.0）
与中枢通信 —— 中枢协议是加密二进制 WebSocket RPC，没有能直接 curl 的接口，xgg 是目前唯一可用的通道。

## 为什么

原来用 xgg 是**命令式**的：一个节点一次 `rule node add`，一条边一次 `rule edge add`。
一条 30 节点的规则要约 60 次调用。实测一批改动 190 次调用跑了 6 分半。

更糟的是**非原子** —— 中间某次调用瞬时失败，就留下一条缺节点的半成品规则，
而 `rule validate` 还会报 `errors: 0`（因为「某个节点没有下游」在图论上不算错误）。

`mgs` 改成**声明式**：期望状态放文件里，一条规则一次 `rule set --body` 整图提交。

| | 命令式 | mgs |
|---|---|---|
| 一条 30 节点规则 | ~60 次调用 | **1 次** |
| 部署一条 20 节点规则（实测） | ~80 秒 | **3.1 秒** |
| 拉 3 条规则（实测） | — | **0.69 秒** |
| 原子性 | 会留半成品 | 要么全落地要么不落地 |
| 能 diff | 否 | 是 |

## 安装

```bash
git clone https://github.com/zealllot/mijia-geek-sync.git
cd mijia-geek-sync
npm i @eyaeya/xgg-cli@2.1.0      # 钉死版本；@latest 会在项目周期内漂移
ln -s "$PWD/mgs" /usr/local/bin/mgs
```

需要：Node 18+、Python 3、macOS 或 Linux（mDNS 解析用 `dns-sd`，Linux 上换 `avahi-resolve` 或直接写 fallback IP）。

## 用法

```bash
mgs init                          # 生成 mgs.json，填网关地址
mgs pull   home                   # 全量拉：规则图 + 变量声明
#   改 data/home/graph/*.json，git diff 看清楚
mgs deploy home --dry-run         # 只看计划
mgs deploy home                   # 建/改，不删
mgs deploy home --prune           # 连线上多余的规则/变量一起删
mgs enable home                   # 看谁开着谁关着
mgs enable home on 20260822110    # 启用
mgs enable home off --match 观影   # 按名字停用
mgs serve  home                   # 开一个本地网页看板
```

**每次操作都要一个 6 位登录码**（米家 App → 中枢网关 → 中枢功能 → 自动化极客版）。
会话闲置会过期，凭证不落盘，所以**做不了无人值守的 CI**。

## 看板

`mgs` 是给你用的命令行；看板是给**住户**用的网页。

![模式看板](docs/images/dashboard.jpg)

住户点某个房间，右边就列出那个房间开灯要过的每一道，断在哪一道标哪一道。
上图里客厅断在「观影模式」，所以后面三道标着「没走到这一步」——
这跟规则实际执行的路径一致，不会让人以为是照度的问题。

（图中「夜灯色温」显示「网关上没有」，是**配置引用了网关上不存在的变量**时的样子。
看板不会把这种情况显示成空值让人以为读到了 —— 见下面第二条不变量。）

```bash
mgs serve 1302                    # 本机开一个看板，浏览器自动打开
mgs serve 1302 --init-config      # 从活着的网关生成语义地图骨架
mgs survey 1302                   # 勘查：设备清单 + 逐台 spec（联机一次）
mgs generate 1302                 # 从 home.toml 生成全部规则（离线）
mgs lint 1302                     # 拿看板的眼睛看一遍：哪些是区、哪个变量是什么角色
tools/build-app.sh --arch arm64 --mdns <实例名> --fallback <IP>
                                  # 打包成自带 Node 的 .app，传给住户双击
```

住户问「客厅为什么不亮了」时，答案分散在三处：某条规则被停用了、某个模式变量
被置位了、或者环境已经够亮所以自动化判断不该开。看板把这三处合成**一句话**。

**它复刻的是开灯规则真实的判定链**，不是自己另发明一套：

```
总闸 ziDongHua==1 → 模式闸 观影/睡眠==0 → 手动锁 shouDong<区>==0
  → 本地照度 < 本地阈值  ──或──  全局照度 < 区阈值
```

整条链读的都是全局变量，所以复刻得了。阈值是规则图里的常量，`--init-config`
直接从图里抠出来 —— 人一个数都不用抄，抄一遍只会抄错，而且改了规则不会同步。

唯一复刻不了的是规则里的「本区灯已灭」（`deviceGet` 设备属性）。极客版的接口
（`getDevList` / `getVarValue` / `getGraph` / `getLog` …）里**没有任何一个能读设备属性**，
所以看板看不到灯此刻是不是亮着。对「为什么不亮」不影响 —— 人来问的时候灯本来就是灭的。

### 四种状态，「够亮了」必须和「受阻」分开

| | 含义 |
|---|---|
| **受阻** | 有东西压着它 —— 手动锁、观影模式、规则停用 |
| **够亮了** | 自动化通着，但环境够亮，它判断不该开 |
| **没发现阻碍** | 我查过的都正常 |
| **未配置** | 这个房间没写进地图 |

第三行的措辞是刻意的。「通」承诺的是「该亮会亮」，而看板永远不可能穷尽所有条件 ——
「没发现阻碍」说的是**检查的范围**，不是结果。

把「够亮了」染成告警色会让住户去关一个根本没问题的开关，所以它用冷色。

### 看板的六条不变量

**1. 白名单记的是「允许写**什么**」，不只是「**谁**能写」。**
可写集合来自配置里显式声明成 `toggle`（开关）或 `number`（可改的数值）的卡片：
开关只收它声明过的那两个值，数值只收 `min`–`max` 界内的数。

只校验身份是不够的 —— 往开关里 POST `999` 也会被原样写进网关。`number` 卡片
**必须**声明上下界：不给界就等于能写任意数，而在别人家里那可能把灯写成
一个谁都没见过的状态。

没有配置文件时白名单是空的，页面纯只读 —— 在别人家里，这是对的默认。

**2. 不做乐观更新。** 写完立刻重读并回显网关的真实值。网关拒绝了、或者规则马上
把它改回去了，页面上要看得出来。

**3. 网关地址是住户填的，不是打包时写死的。**
IP 由 DHCP 分配，会变。写死一个意味着地址一变，住户就只能等你重新打包 ——
所以地址在登录页上和 6 位码一起填，默认值是他**上次登录成功**用的那个。
登录失败不落盘（存一个连不上的地址会把下次的默认值弄坏），但页面上留着他刚填的，
好让他改错字。也收 mDNS 实例名 —— 那个比 IP 耐用，换 IP 不用改。

**4. 看板只写变量 —— 唯一的例外是区阈值，而那一处两头上锁。**
区阈值不是变量：`deviceGet` 的比较值只收字面量（不能引用变量），所以它是规则图里
`A3b` 节点上的常量 `v1`。要在页面上改它，只能改图。

这是看板唯一会写规则图的操作，所以：

- **默认不给改。** `--init-config` 生成的骨架只带 `zoneThresholdNode`（改哪个节点），
  不带 `zoneThresholdRange`（能改到多少）。**你得逐个房间手动加范围才会变成可改**。
- **补丁做到最小。** xgg 的 `updateNode` 是 `{...existingNode, ...patch}`，
  **`props` 不深合并**（只有 `cfg` 合并一层）—— 只传 `{"props":{"v1":N}}` 会把
  `did`/`siid`/`piid`/`operator` 全抹掉。所以要把原 props 整个带上，只换 `v1`。
  还必须带上原样的 `cfg.pos`，否则 `updateNode` 会重算 card geometry 把坐标改掉，
  下次 pull 就是一个假 diff。
- **写完回读整张图逐字段比对。** 「只改了这一个」不能靠嘴保证 ——
  这是在别人家里改正在跑的自动化。有第二处变了就报出来、指向快照，并写进审计日志。
- **本地阈值（那个 100）不给改。** 它是全屋共用的舒适下限，不是按区标定的。

### 改完参数要补一发脉冲（`applyWith`）

极客版的 `varChange` 对同一个变量**只监听得到一次**。1302 的规则用「写 1 →
执行链第一步写回 0」的翻转法绕开这个限制：

```
同步 变为 1 ──→ 同步 = 0 ──→ 17 路判亮 → 写亮度 ‖ 写色温
                  ↑ 归零，所以下次写 1 还能响
```

代价是「改参数」和「让它生效」变成两步。**第二步不该让人自己记着去戳**，
所以卡片可以声明改完往哪发脉冲：

```json
{ "kind": "number", "title": "全局亮度", "scope": "global", "id": "quanJuLiangDu",
  "min": 1, "max": 100, "unit": "%",
  "applyWith": { "scope": "global", "id": "tongBu", "value": 1 } }
```

**脉冲的目标不进可写白名单** —— 它由服务端在写入成功后自己发，页面不能直接写，
不然它就成了一个谁都能戳的裸开关。页面上这类卡片标一个 `⇢`，
跟「只是存个数、要等别的时机才生效」的区分开。

**注意它和 `mgs deploy` 的关系**：住户改完阈值，你本地的 graph 文件就旧了 ——
下次 deploy 会覆盖回去。`mgs pull` 的 diff 看得见，但你得记着先 pull。

**5. 外观和语义分开存。**
`dashboard.json` 是你手写、进 git 的**语义地图**：房间叫什么、闸门链是什么、
阈值能改到多少。页面上摆出来的**外观**（房间和卡片的位置、背景图/底色）
存在 Application Support 的 `layout.json` 里，页面自己写。

分开的理由：住户在页面上把房间挪个位置，不该让你的 git 产生 diff；
而你改语义配置，也不该把他摆好的位置冲掉。合并时 `layout.json`
**只能覆盖位置四个字段** —— 它改不了房间归哪条规则、闸门链是什么。

外观包括：房间和卡片的位置、背景（图片 / 渐变 / 纯色）、以及卡片底色、透明度、
描边色、文字色、圆角。

**整套配色都从 `--ink` / `--panel` / `--line` 派生**，页面里没有写死的灰阶。
写死的灰只在一种底色上成立 —— 铺一张浅色背景图，深色调的次要文字就全看不见了。

`layout.json` 是页面写的，所以读回来时当不可信输入清洗：位置夹到合理范围，
颜色必须是十六进制（那些值会进 CSS 变量），图片文件名挡住路径穿越。

**5b. 分组可以在页面上改，但页面只送「谁归哪组」。**
编辑模式里能新建分类、改名、删掉，把「未归类」里的东西挪进去
（点一张卡，再点分类标题）。删掉分类不会删掉卡片 —— 它们回到未归类。

页面**只送 ref**，不送卡片定义：定义决定写入白名单的边界（开关认哪两个值、
数值的上下界），让页面送定义等于让它自己定边界。定义要么沿用配置里已有的，
要么按图里推出来的角色生成。

挪出分组的定义会存进 `retired`。手写的 `min/max/unit/applyWith` 猜不回来，
挪出去就丢的话，拖错一下、一个能用的滑块就永久变成只读了。

**6. 房间是从规则图现推的，配置只是一层覆盖。**
每次刷新，服务端把这户所有规则的图拉回来（缓存 10 分钟），从里面**推出**有哪些区、
每个区的闸门链是什么、阈值是多少 —— 判据是结构而不是名字：一条规则里存在照度比较，
它就是一个区；能走到那个比较的全局变量等值判断，就是这个区的闸门。

所以 `dashboard.json` 里已经**不需要**再写 `chain` 和 `lux`。它现在只剩人写得出、
机器猜不出的那部分：

| 字段 | 作用 |
|---|---|
| `title` | 区叫什么（规则里叫「沙发」，住户叫「客厅」） |
| `x/y/w/h` | 在平面图上摆哪儿 |
| `say` | 某道闸门挡住时说人话（`{ "huiKe": "会客模式开着" }`） |
| `hide` | 哪几条规则不当区（1302 的电梯口、电梯玄关） |

**这条是为了让「改完自动化要重新抠、重新打包、重新装」这个循环消失。**
你在米家里加一道闸、改个阈值、甚至新建一个区，看板几分钟内自己就跟上了。
没写覆盖的区照样出现，只是用规则里的原名、按顺序往下摆。

拉不到图时（网关连得上但 `rule list` 失败）退回配置里存的那份 —— 所以老配置里
留着的 `chain` / `lux` 不是废字段，是离线兜底。

**7. 卡片是什么，也从规则图推。**
每个全局变量「是什么」，规则图里已经写着了 —— 看板照着读，不用人再抄一遍：

| 图里的写法 | 看板的理解 |
|---|---|
| `deviceGetSetVar` 把设备读数写进变量 | 传感器快照，**只读**（人写进去会被下次采样盖掉） |
| `deviceOutput` 把变量写进设备属性 | **参数**卡；节点上带 `min`/`max`/`step`，上下界直接用它 |
| `varGet` / `varChange` 拿变量做等值判断 | **闸门**；取值只有 0/1 就是模式**开关** |
| `varChange` 触发 + 第一步写回 0，且从没人 `varGet` 它 | **翻转变量**，是脉冲目标，自己不出卡 |

比让人写配置强的地方不只是省事。1301/1302 的全局色温人手写的是 `2700-6500`，
而图里所有灯的交集是 `3000-6400` —— 按手写的那份，住户能把某盏灯写进它不认的值。
**范围只收紧不放宽**：图里更窄就按图里的，人写得更窄就听人的（可能是故意收着的）。

两处容易漏的：参数常常**先抄进规则域变量再写设备**
（`夜灯亮度 → R…001.bri → 灯`），上下界在下一跳，所以推导得跟着别名走；
而同一个中转变量在一条规则里可能有**好几个来源**（夜间分支抄夜灯亮度、
白天分支抄全局亮度），只记最后一个的话，前面那个参数永远推不出来。

**一户全新装上来、一个字的配置都没有时，整份现推**：房间从开灯规则来，
卡片按角色自动分成「全屋模式」和「参数」。装上打开就能用，不用先回终端生成配置。

`mgs lint <网关>` 把这套推导的结果打出来 —— 改完自动化跑一下，
就知道看板会把这户理解成什么样，不用装一遍才发现少认了一个区。

**8. 只绑 `127.0.0.1`。** 住户家 WiFi 上的其他设备不该能翻他家的模式开关。
写接口另外要一个持久化的 token（存在 Application Support，0600）——
浏览器里任何一个网页都能往 `127.0.0.1` 发请求，这是本地服务的经典问题。

### 换背景、改配色、摆位置

![编辑模式](docs/images/edit-mode.jpg)

右上角「编辑」进编辑模式，顶部出现两行控件：

| | |
|---|---|
| **背景** | 无 / 渐变（两色 + 角度）/ 图片（可调模糊、变暗）/ 纯色 |
| **外观** | 卡片底色、透明度、描边色、文字色、圆角，以及「恢复默认」 |

**拖房间挪位置，拖右下角改大小。** 全屋模式那排卡片不能拖也不能缩放 ——
它们本来就是等宽的，拉大小只会拉歪；改成**点 A 再点 B 交换位置**。

改完点「保存」才落盘，「取消」全部丢弃。编辑期间会暂停轮询，
不然每 10 秒重画一次会把拖到一半的东西冲掉。

**透明度是这里最要紧的一个。** 铺了背景图之后不透一点，就等于把图整个盖住。

整套配色都从 `--ink` / `--panel` / `--line` 派生，页面里没有写死的灰阶 ——
写死的灰只在一种底色上成立，铺一张浅色背景图就会让次要文字全看不见。

外观存在 `~/Library/Application Support/MijiaDashboard/layout.json`，
**和语义配置分开**（见上面第五条不变量）。住户怎么摆都不会让你的 git 产生 diff。

### 第一次打开：填地址和登录码

![登录](docs/images/login.jpg)

地址在上、登录码在下，地址预填**上次登录成功**用的那个。
路由器重启后连不上，就在同一个页面上改地址 —— 不用等你重新打包。

也收 mDNS 实例名（比 IP 耐用，换 IP 不用改）。
登录失败不落盘，但页面上留着刚填的，好让人改错字。

### 多户：切换房屋

一台机器可以管几户。**一户 = 一个网关 + 一份语义地图 + 一套外观**，三样一起切 ——
两户的房间、闸门链、平面图位置都不一样。

```json
// houses.json
[
  { "id": "1302", "name": "1302",      "mdns": "xiaomi-gateway-hub1",   "fallback": "192.168.5.25" },
  { "id": "1301", "name": "1301 楼下", "mdns": "xiaomi-gateway-hub1-2", "fallback": "192.168.5.33" }
]
```

每户的语义地图和外观各存一份：`dashboard.<id>.json` / `layout.<id>.json` /
`address.<id>.json`。**没有 `houses.json` 就是单户模式**，文件名不带后缀 ——
跟已经发出去的包兼容。

**房屋在页面上管**：顶栏的「房屋…」可以新增、删除、以及给当前这户**生成房间地图**
（就是原来只能在命令行做的 `--init-config`，搬到了页面上，新加一户不用回终端）。

**`id` 自动生成，跟名字无关。** 名字是给人看的（中文、斜杠、空格都行），
`id` 是拼文件名的。分开之后：改名不动文件、两户重名也没事、
名字里的斜杠不会跑进路径。

**删除是挪进 `trash/`，不是直接删** —— 手工调过的语义地图（房间、闸门链、话术）
没了是找不回来的。

管理入口**始终显示**，哪怕只剩一户或零户。早先它和切换器绑在一起、
只在两户以上才画，结果删到只剩一户就再也加不回来了。

```bash
tools/build-app.sh --arch arm64 --houses houses.json \
  --house-config 1302:data/1302/dashboard.json \
  --house-config 1301:data/1301/dashboard.json
```

**会话不用管。** xgg 的会话按网关分条存，所以切过去登录过就直接能用、没登录过就
落到登录页，两户互不影响。登录页和「连不上」那一屏也带切换器 ——
不然某一户连不上就卡死在那户了。

`id` 会被拼进文件名，所以只收 `[A-Za-z0-9_-]`：不挡的话等于让配置指定读写哪个文件。

### 退出登录 ≠ 退出程序

页面底部两个按钮是两件事：

| | |
|---|---|
| **退出登录** | 结束这台网关的会话（`xgg logout`，停掉 per-host agent 并删会话条目）。**地址保留** —— 退的是登录不是忘掉网关，重登只用填 6 位码 |
| **退出** | 停掉服务。会话还在，下次打开直接是登录状态 |

要退出登录的场合：地址填错了想换一台网关（得先把旧会话放掉）、
或者住户想收回看板的访问权。

会话文件按网关分条存，所以**一台机器可以同时登录多台网关**，互不干扰。

### 打包给住户

`.app` **自带 Node 运行时**（~40MB zip）：xgg 硬要求 Node ≥ 20.11，而 macOS
从 12.3 起不再自带 python3，也从来不自带 node。「双击就能用」就得自带。

自带 Node 也是服务端用 Node 而不是 Python 的原因 —— 既然无论如何要带一个运行时，
再带第二个就是白花的体积和复杂度。但**子进程边界不能破**：xgg 是 GPL-3.0，
mgs 是 MIT，这个组合成立只因为两者是独立进程，`import` 会让 mgs 变成衍生作品。

```bash
tools/build-app.sh --arch arm64|x64 --config data/1302/dashboard.json
```

**`--config` 不给的话，住户打开是扁平只读模式** —— 没有房间平面图、没有闸门链、
没有那句结论，也什么都改不了。脚本会明确警告。

`--arch` 必须显式给：这是给**别人**机器打的包，用本机架构会打出一个在对面跑不起来的东西。
不确定就两个都打，他解错了打不开，没有别的后果。

`.app` 没有签名。通过网络传过去会带 quarantine 标记，住户首次打开要去
「系统设置 → 隐私与安全性」点「仍要打开」。只痛一次。

**以后要改配置不用重打包。** 服务端找配置的顺序是
`~/Library/Application Support/MijiaDashboard/dashboard.json` → 包里那份，
所以把新的 JSON 发过去让住户放进那个目录就行，**不用重启 app**，下一轮轮询就生效。
（比如要开某个房间的阈值编辑，就是给它的 `lux` 加一行 `"zoneThresholdRange": [1, 3000]`。）

## 三条不变量

**1. `deploy` 永不改变规则的启用状态。**
`rule set` 默认 `cfgPreserved`，线上是启用就保持启用、是停用就保持停用。
文件里的 `cfg.enable` 是**记录，不是控制**。启用是单独的决定，走 `mgs enable`。

在别人家里动自动化时，「把规则部署上去」和「让它开始跑」必须是两个决定。

**2. `deploy` 永不覆盖已存在变量的值。**
极客版的变量里混着两类东西：

| 例子 | 性质 | 部署时 |
|---|---|---|
| 全局亮度、色温、各区照度阈值 | 配置 | 缺了就按文件里的初值创建 |
| 「自动化总开关」「睡眠模式」「手动锁」 | **运行时状态** | **绝不碰** |

覆盖第二类等于把住户正在生效的模式清掉。`mgs pull` 会按配置里的 `runtimeVars` 正则
把这类变量的初值记成 `null` 并打 `runtime: true`，顺带避免每次 pull 产生假 diff。
规则域变量（scope 以 `R` 开头）一律算运行时。

**3. 不给 `--prune` 就绝不删。**
`--prune` 之前会自动做一次整机备份；本地 `graph/` 为空时直接拒绝执行
（防止一次失败的 pull 把中枢清空）。删规则时先删它的规则域变量再删规则，不留 ghost data。

## 给新一户配置

一次上门跑完，步骤在 [docs/新一户.md](docs/新一户.md)。核心是：**规则不再手建**。

```
mgs survey  <户>   联机一次，拉设备清单 + 逐台 MIoT spec → devices.json
（走一圈写 homes/<户>.toml：区、目标、开关键）
mgs generate <户>  离线生成全部规则，每条 xgg rule validate --body 校验
mgs deploy  <户>   在他家局域网内推上去
```

`home.toml` 里只写机器猜不出来的东西。**能推的都推**：

| 闸门 | 从哪推出来 |
|---|---|
| `ziDongHua=1` | 默认每个区都有；`master = false` 才退出 |
| `shouDong<区>=0` | 这个区声明了 `switches`，且 `[house] manualLock` 开着 |
| `<场景变量>=0` | `[[scene]] zone` 指到这个区 |
| `huiKe=0` | 这个区在 `guestMode.zones` 里 |

拿两户做过回归（`tools/compare-graphs.py` 比结构，忽略 id、坐标、画布便签）：
**1301 20/20 完全一致，1302 29/42**，差的多是场景规则 ——
生成器把动作统一放执行规则，而 1302 手建时把灯放在了意图规则里，语义等价、布局不同。
两户 63 条规则压缩成 276 行 TOML，其中真正的「例外」只有三行。

**节点不手写**：每种节点从 `shapes/` 里那份「形状」深拷再填值（[ADR-0002](docs/adr/0002-shape-library-not-graph-templates.md)）。
形状是从真实规则图抠出来再脱敏的，所以 schema 天然对；拼错了由离线校验器当场兜住。

**阈值和延时不归生成器**（[ADR-0001](docs/adr/0001-generator-owns-structure-gateway-owns-tuned-values.md)）：
本地已有这条规则的图就沿用图里的当前值，只有新建的区才用 `home.toml` 里的初值。
所以重新生成的 diff 里只会出现结构变化。

**区的槽位一旦分配就固定**，记在 `generated.json` 里。按区在 toml 里的位置编号是错的 ——
删掉中间一个区，后面所有区的规则 id 全部前移，`deploy --prune` 会把一屋子规则删了重建。

## 装在 Windows 上

住户的电脑不一定是 Mac（[ADR-0004](docs/adr/0004-dashboard-runs-on-windows-too.md)）。
看板本体跟平台无关，钉死的只有四处，都收在 `dashboard/lib/platform.mjs` 和两个打包脚本里：

| | macOS | Windows |
|---|---|---|
| 打包 | `tools/build-app.sh --arch arm64\|x64` | `tools/build-win.sh` |
| 形态 | `.app`，拖进「应用程序」双击 | 文件夹 + 双击「模式看板.cmd」 |
| 状态目录 | `~/Library/Application Support/MijiaDashboard` | `%APPDATA%\MijiaDashboard` |
| 开机自启 | LaunchAgent plist | 「启动」文件夹里的 `.cmd`，删掉＝关掉 |
| 首次拦截 | Gatekeeper「仍要打开」 | SmartScreen「更多信息 → 仍要运行」 |

**两个包都在 Mac 上打**，Windows 那个只是解压一个 win-x64 的 node 再拼文件，不编译。

**mDNS 不再走 `dns-sd`**（那是 macOS 独有的命令）。`dns.lookup('<名>.local')`
两边都通：macOS 走 Bonjour，Windows 10+ 的 DNS 客户端自己解析 `.local`。

## 踩过的坑（都已固化进代码）

**原生 body 和 CLI 参数是两套语言。** `rule view` 返回的原生图能直接 `rule set` 推回去，
但字段名和 `rule node add` 的参数对不上：

```
--var-id X   →  "id": "X"
--op eq      →  "operator": "="
--expr 1     →  "elements": [{"type":"const","value":"1"}]
```

所以**新节点要从真实节点克隆形状，不要手写** —— 猜的会被 schema 拒（好在它拒得很明确）。

**格式化绝不能重排数组。** 早期版本为了让 diff 稳定，对 `nodes` 和 `outputs` 排了序，
结果那个重排被当成内容写进了中枢，把某个节点的**扇出顺序**改掉了（边的集合没变，
但下发顺序变了）。实测中枢返回的顺序本身是稳定的，所以排序既没必要又有害。
现在只排序 JSON 的 key。

**别把 xgg 的输出接进 `head`。** SIGPIPE 会把文件截成 0 字节，而且不报错。

**`rule view` / `rule list` 会偶发返空且不报错**（退出码仍是 0）。所有读取都带重试 ——
但**判据必须是「能解析成 JSON」而不是文件大小**。早期版本用「小于 60 字节 = 失败」，
在一台没有规则域变量的中枢上把合法的 `variable list`（只有 32 字节）当成了失败。

**`dns-sd` 的第一行不是数据。** 早期用 `awk '/^[0-9]/{print $6; exit}'` 取地址，
但 `...STARTING...` 那行也以数字开头 —— 于是它匹配到那行、打印出空的地址列就退出，
**mDNS 解析从来没成功过**。因为每次都静默回落到 `fallback`，所以一直看不出来，
直到 DHCP 换了地址、本该救场的 mDNS 并不救场。而且第一条 `Add` 可能是回环地址
（解析本机名时 `127.0.0.1` 排在前面），取「第一条」会让工具去连自己。
判据得是：`A/R` 列是 `Add`、地址列是像样的 IPv4、且不是 `127.` / `169.254.`。

**mDNS 解析不了的时候，`fallback` 得真的被试到。** 启动时按「住户填过的地址 →
房屋声明的 mDNS 名 → 房屋声明的 IP」逐个试，早先的写法只试第一个就放弃 ——
于是换了网段（或路由器不转发 mDNS）时，页面显示登录屏、地址栏里预填着一个
解析不出来的实例名，那个本来就是为这种情况准备的 IP 从来没被用上。

**mDNS 实例名在别的网段会指向别人的设备。** `xiaomi-gateway-hub1` 这种名字并不唯一，
不在那户家里的时候解析它，很可能解析到一台毫不相干的机器上去。
所以离线验证一律用假 xgg，测试配置里的地址写 `127.0.0.1`，不往真网段发包。

**Windows 的 `.cmd` 里不能用 `for /f` 读一个不退出的命令的输出。**
`for /f` 会**等命令跑完**才处理输出，而看板服务永远不退出 —— 照搬 macOS 那套
「读 READY 行再开浏览器」，浏览器就永远打不开。改成让服务自己开（`MGS_DASH_OPEN=1`）。

**规则图里 `dtype` 是按节点类型定的，不是属性的固有属性。** 比较节点
（`deviceGet` / `deviceInput`）写 spec 的格式（`int` / `float`），而变量写入节点
（`deviceGetSetVar` / `deviceOutput` 的变量形态）一律写 `number`。
混着记会把 `number` 塞进 `deviceGet`，校验器报 `Invalid dtype`。
同理 `delay` / `loop` 的时长在 `cfg.value/unit` 和 `props.timeout` 里各存一份，
必须一致，单位只认 `ms` / `s` / `min` / `hour`。

**`ok:false` 不能当数据用。** 未登录时 `variable watch` 返回 `{"ok":false,...}`，
它能正常解析成 JSON，于是归一化时 `variables` 退成 `{}` —— 「没登录」被伪装成
「网关上什么都没有」，看板理直气壮地显示「一切正常，0 项」。读取路径必须把
`ok:false` 变成异常。（但**不要重试它** —— `AUTH_REQUIRED` 是确定的答案，
每 10 秒轮询重试三次纯属浪费。重试只给「空输出 / 解析不了」。）

**从规则图抠东西要按拓扑，不能按顺序。** 1302 的开灯规则里 `A4`（读 `yeJian`）
在节点数组里排最前面，但它是输出段的**昼夜分支**，不是闸门。按顺序抠会把它当成
放行条件，于是白天 `yeJian=0` 时看板说「受阻：夜间模式不是 1」，全错。
判据只能是「这个节点能不能走到照度比较」。同理，场景规则（「全屋开灯」）名字里
也含「开灯」，要按**有没有照度判定**来排除，不能按名字。

**bash 里 `$var` 紧跟中文会炸。** `$fail）` 中的全角括号是多字节，bash 会把它当成
变量名的一部分，`set -u` 下直接报 unbound variable。写中文提示时一律用 `${fail}`。

**`validate` 和 `lint --strict` 查的不是一回事。** `validate` 查 pin、颜色、fan-in、
spec 和量程；`lint --strict` 还会查**卡片不可达**（某个输出永远不会被触发）。
批量改动后两个都要跑 —— 只看 `validate` 会漏掉「节点压根没加进去」。
`rule enable` 自己也跑可达性检查并拒绝启用坏图，这是个很有用的兜底。

**坐标存在文件里，所以不需要 `rule layout`。** 节点位置是期望状态的一部分，
每次部署都一样，diff 干净。

## 限制

- 只覆盖**规则图和变量**。设备、灯组、传感器参数都在米家 App 侧，本工具碰不到 ——
  网关的接口里没有任何一个能读设备属性，所以看板也看不到灯此刻亮不亮。
- 依赖 xgg（非官方、逆向）。米家固件或前端一升级就可能失效。
- 鉴权必须人工取码，所以没有无人值守的可能。
- 只在自动化极客版 `ai-config-v5`（2026-04 构建）上验证过。
